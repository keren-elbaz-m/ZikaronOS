הגרסה החרדית, "זיכרון בבית"

אותו קוד, build נפרד עם הדגל REACT_APP_ORTHODOX_MODE. הוא מחליף טקסטים, כותרת ו-favicon, וסוגר את הרשמת האורחים. נבדק בכ-22 קומפוננטות ובטבלת ה-routes.

איך הקוד בנוי בפנים 699 קבצים ב-src/

שלוש דרכים לקרוא ל-API, ורק אחת מרעננת token

קריאות axios ישירות (התחברות, הרשמה), ה-instance המשותף (רוב המסכים, מרענן אחרי 401), ו-actions שנושאים בקשה. רק השני מרענן token, השאר פשוט נכשלים כשה-token פג.

בקרות שכבר קיימות נבדקו מול החשבון החי

  • HTTPS ו-WAF. CloudFront עם managed rules ו-bot control לפני האתר.
  • האתר הוא קבצים בלבד. אין שרת ואין מערכת הפעלה לתחזק או לפרוץ.
  • תעודה בתוקף לדומיין של האתר, עד 2027.
  • build אוטומטי לכל ענף וניקוי cache אחרי כל העלאה.
  • אין בקבצים מידע של משתמשים. הנתונים מגיעים רק מה-API, אחרי התחברות.

מגבלה שכדאי להגיד מראש

כל מה שנמצא בקוד של האתר מגיע לכל מבקר. מפתח, secret או בדיקת הרשאה שיושבים שם הם ציבוריים בפועל. ההגנה האמיתית יכולה להיות רק ב-API.

מה לא תלוי בהחלטת האירוח

כתובת API בלי ברירת מחדל ל-dev, בלי secrets בקוד הלקוח, טסטים ובדיקות בכל build, והסרת העותק הישן של הניהול. כל אלה נכנסים לשכתוב בכל מקרה.

להחלטה

א. איפה מארחים את האתר ואת פורטל הניהול בשכתוב (Next.js)

  1. AWS Amplify לשניהם. כבר בשימוש לפורטל, תומך ב-server rendering של Next.js וב-build ישר מ-GitHub. מומלץ
  2. S3 + CloudFront עם static export, כמו היום. פשוט וזול, אבל בלי server components ובלי SSR.
  3. containers ב-ECS מאחורי CloudFront. שליטה מלאה, אבל עוד image לתחזק ולסרוק בכל סביבה.

ב. האם ה-API נכנס מאחורי CloudFront ו-WAF

היום הדפדפן פונה ל-API ישירות. אם ה-API יעבור מאחורי אותו CloudFront (/api/*), ה-WAF יגן גם עליו ויהיה דומיין אחד לאתר ול-API.

ג. חסימת מבקרים מחוץ לישראל

האתר בודק מדינה דרך ipapi.co ומצפה ל-HTTP 450 מה-API, שאף אחד לא שולח. לשמור חסימה בשכתוב, או לוותר?
